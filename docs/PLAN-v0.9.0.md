# OAA v0.9.0 - Ontology as Prompts

**Status:** Draft for review - **Date:** 2026-10-24 - **Depends on:** v0.8.0 (`docs/PLAN-v0.8.0.md`)

## Scope

The ontology server (`ontology/`), its skill (`skills/oaa-ontology-design/`), and the
ontology parts of the docs. These ship unchanged in 0.8.0, so 0.8.0 is prompts plus one
compiled MCP server (`oaa-ontology`) until this release.

**Why separate:** replacing the checker, the `.rel` -> SQL mapping, and the runtime store
with prompts is the largest piece of work in the OAA rewrite. It has no estimate yet
and needs its own planning pass before it starts.

## Decision

**D7:** keep the `.rel` language. Add `compile-ontology.prompt.md`, which emits
`ONTOLOGY.md` and `schema.sql`. Drop the runtime store tools (`compile_schema`,
`write_entity`, `query_concept`), because runtime memory belongs to the runner, not to
OAA. Companies that call `write_entity` today must move that storage to the runner.
The alternative is to remove the ontology skill entirely until it has a runtime.

**Open question:** fold `oaa-ontology-design` into the main skill as a prompt, or keep it
separate with plain-file outputs only.

## Phases

4. Update `skills/oaa-ontology-design/SKILL.md` per D7, and remove its MCP tool
   references. Remove the ontology runtime section from `org-agent-architecture/SKILL.md`
   and the `get_ontology` references from `README.md`.
5. Delete `ontology/` (src, dist, package files, README). Move `ontology/CHANGELOG.md`
   into the root `CHANGELOG.md`.
6. Remove the `oaa-ontology` entry from `plugin.json`, the ontology hook from
   `hooks.json` (delete the file if nothing is left), and `!/ontology/dist/` from

8. Run T10 (no MCP entries left, no hook errors) and T12. Release as `0.9.0`.

## Rules

With no checker, the only thing between a typo in a `.rel` file and a broken
ONTOLOGY.md is the prompt. The prompt has to read like the code it replaces: numbered
rules, each with MUST or MUST NOT, a severity, and a refusal to write output when any
error-level rule fails.

Each rule the TS layer enforces is carried over **one-for-one** from
`ontology/src/checker.ts` and `validator.ts`. Extract the list first, then delete.

| Rule (from the code) | Prompt form | Severity |
|---|---|---|
| Names unique within an ontology | MUST NOT declare a name twice | error |
| `type X extends B`: B is built-in | MUST extend only: {built-in list, verbatim} | error |
| Entity `identified-by` type is declared | MUST declare the identity type before use | error |
| Every concept has an `identity` | MUST give every entity a stable business key | error |
| Property types are known | MUST use a declared or built-in type | error |
| Relation targets are declared (or imported) | MUST resolve every relation target; cross-domain targets MUST be in `imports:` | error |
| Relationship cardinality is valid | MUST use one of: {list} | error |
| Derived entity extends a declared **base** entity | MUST NOT derive from a derived entity | error |
| Expression properties exist on the entity | MUST reference only declared properties | error |
| Tool-map concepts and properties exist | MUST map only to declared concepts and properties | error |
| Concept names PascalCase; property names lowercase-hyphenated | MUST follow casing | warning |
| Business vocabulary, not API/schema names | MUST use business verb phrases and names | warning |
| Property typed as another entity's identity key | Flag as possible FK written as a plain property | warning |
| Unknown identifier in expression | Flag as a possible typo | warning |
| Tool map missing an entity | Flag and ask | gap |
| `write_entity` rejected unknown fields (runtime) | Skills MUST write only properties declared in `.rel`; the validate prompt checks skill bodies for undeclared field names | warning |

**Output contract:** the prompt lists every finding with its rule number before
writing anything. If any error-level finding exists, it writes nothing and stops.
`schema.sql` is generated by fixed mapping rules (type -> SQL type table, derived
entity -> `CREATE VIEW ... WHERE <expr>`), stated as a table in the prompt, not left to
judgment.

## Risks

- **Phase underestimated.** The `.rel` -> SQL mapping and the runtime store removal are
  the hardest parts. It may need its own release candidate.
- **Breaking for runtime users.** Any company calling `write_entity` or `query_concept`
  breaks at 0.9.0. Write a migration note before release.
