# Slide 7 — The Ontology: Domain Vocabulary in `.rel`

**Title:** The Ontology: Naming What Your Authority Actually Means
**Tagline:** `.rel` source files → compiled SQLite entity store + ONTOLOGY.md

---

## Key Message

Authority identifiers like `subscriber-list` and `campaign-budgets` appear in `owns` and `decides` blocks, but without an ontology they are just labels. The OAA ontology layer gives each identifier a formal definition — its properties, its data types, and derived concept rules that skills can query without re-hitting external APIs.

---

## The `.rel` Language

`.rel` source files live in the `ontology/` directory. They declare three things:

### Entity Declarations
```rel
entity Campaign {
  id:           string  @key
  name:         string
  status:       string
  daily-budget: float
  rolling-3day-cpa: float @computed
}
```

### Derived Concept Rules
Concepts are named subsets of entities, defined by a condition. Skills query these rather than calling external APIs:

```rel
concept UnderachievingCampaign extends Campaign {
  where rolling-3day-cpa > 35
}

concept PausedCampaign extends Campaign {
  where status == "paused"
}
```

### Relation Declarations
```rel
relation owns Campaign -> AdAccount
```

---

## Compilation

`compile_ontology` (via `@oaa/ontology` MCP server) processes `.rel` sources and produces:

| Output | What it is |
|---|---|
| `ONTOLOGY.md` | Human- and agent-readable reference; injected into AGENTS.md |
| `schema.sql` | DDL for the entity store tables |
| `memory/ontology.db` | SQLite database — the runtime entity store |

---

## Runtime: write_entity and query_concept

At run time, two MCP tools operate against the entity store:

- **`write_entity`** — skills call this to persist values observed from external APIs (campaign status, budget, CPA). Values are always written to the store, never hardcoded in prompts.
- **`query_concept`** — roles call this to read derived concept views. `query_concept("UnderachievingCampaign")` returns all campaigns where `rolling-3day-cpa > 35` without re-calling the Ads API.

This is how OAA keeps roles separate from data-fetching: the skill writes, the role queries.

---

## The MCP Server

The `@oaa/ontology` MCP server exposes:

| Tool | Purpose |
|---|---|
| `compile_schema` | Compile `.rel` → `schema.sql` |
| `compile_ontology` | Compile full ontology → `ONTOLOGY.md` + SQLite store |
| `validate_ontology` | Check `.rel` sources for type errors and broken relations |
| `get_concepts` | List all declared concepts and their conditions |
| `write_entity` | Persist a runtime entity value |
| `query_concept` | Query a derived concept view |

Requires Node 22.5+ (`--experimental-sqlite` is enabled via `NODE_OPTIONS`).

---

## Speaker Notes

- The ontology is **optional** — most OAA graphs work fine without it. It becomes valuable when multiple roles need to agree on what `UnderachievingCampaign` means, or when a role needs to query structured data without duplicating API calls.
- The SQLite store lives at `memory/ontology.db` — inside the agent's `memory/` folder, so it persists across activations and is excluded from `agents.lock` hashing (it's runtime state, not node identity).
- Skills write entities. Roles query concepts. Never the other way around — this is how OAA separates data access from decision-making.
- `ONTOLOGY.md` is generated by `compile_ontology` and injected into `AGENTS.md` by `compile_agent`. An agent's full system prompt includes the compiled ontology reference automatically.
- The install command for the ontology server: `env NODE_OPTIONS=--experimental-sqlite npx -y github:Chuck3PointZero/OAA#v0.4.0:ontology`
